# AX-CAD 개발 문서 (docs/)

`docs/`는 AX-CAD를 무엇을, 어떻게, 어떤 순서로 만들고 검증하는지 정의한 **7단계 개발 문서 묶음**이다.
**언제** 하는지는 루트의 [`plan.md`](../plan.md)가 정한다. 이 README는 둘을 연결하고 문서 관리 규칙을 정의한다.

```text
plan.md  ── 일정·방법론·게이트·스프린트 (언제, 어떤 순서로)
   │  ▲
   ▼  │  산출물 제출 / 변경 반영
docs/    ── 요구사항 → 기능 → 화면 → 디자인 → 개발 → 테스트 (무엇을, 어떻게, 어떻게 검증)
```

## 3. 추적성 체인

모든 산출물은 ID로 연결된다. 한 항목을 바꾸면 체인을 따라 영향 범위를 확인한다.

```text
REQ-xx (SRS) ─▶ FN-xx (기능 명세) ─▶ SCR-xx (IA/와이어프레임) ─▶ 코드(커밋 메시지에 FN-xx)
                                                                    │
       릴리스 판정 ◀── 테스트 보고서 §6 ◀── TC-xx 결과 ◀──────────────┘
```

| 규칙 | 내용 |
|---|---|
| ID는 재사용하지 않는다 | 삭제된 요구사항은 `~~REQ-xx~~ (삭제: 사유, 날짜)`로 남긴다 |
| 커밋·PR에 ID 기재 | 예: `feat(dxf): expand INSERT blocks (FN-14, TC-61)` |
| 모든 REQ는 FN·TC를 1개 이상 가진다 | RTM에서 빈칸이 생기면 게이트·스프린트 리뷰를 통과하지 못한다 |

## 4. 문서 관리 규칙

### 4.1 이름과 위치

- 파일명: `[단계번호].AX-CAD_[산출물명].md` (예: `2.AX-CAD_기능명세서_PRD-FS.md`)
- 부속 문서(ADR, OpenAPI 등)는 번호 없이 둔다: `docs/openapi.yaml`, `docs/adr/ADR-xx-제목.md`(필요할 때 생성)

### 4.2 버전 규칙

| 변경 | 버전 | 예 |
|---|---|---|
| 오탈자·표현 수정 | 그대로 | V1.0 |
| 내용 보완(범위·의미 변화 없음) | 소수점 증가 | V1.0 → V1.1 |
| 게이트 승인으로 기준선 확정 | 정수 증가 | V1.x → V2.0 (G1·G2·G3 시점) |

각 문서 상단 버전을 올리고, 아래 §6 변경 이력에 한 줄을 추가한다.

### 4.3 변경 통제 (Hybrid 규칙)

| 시점 | 수정 방법 |
|---|---|
| **G3 이전** (W1~W3) | 자유롭게 수정. 게이트 리뷰에서 승인 |
| **G3 이후** (스프린트 중) | 기준선 문서(1~6) 수정은 **변경요청(CR)**으로만 한다 |
| 테스트 보고서(7) | 스프린트 중 상시 갱신 (CR 불필요) |

**CR 절차**

1. 변경 사유와 대상 ID(REQ/FN/SCR/TC)를 적는다.
2. 추적성 체인(§3)으로 영향 문서·스프린트를 확인한다.
3. PO·기술 리드가 승인한다.
4. 문서를 수정해 버전을 올리고 §6에 기록한다. 일정에 영향이 있으면 `plan.md`의 스프린트·마일스톤도 함께 고친다.
5. 다음 스프린트 Planning에 반영한다.

### 4.4 문서 간 동기화 체크

한 문서를 고치면 다음 연결 문서를 함께 확인한다.

| 수정한 곳 | 함께 확인할 곳 |
|---|---|
| SRS REQ 추가·삭제 | 기능 명세 §1, RTM, `plan.md` 범위(§8) |
| FN 추가·변경 | IA 화면 목록, 와이어프레임, 스택 API 목록, TC |
| 데이터 구조(IA §4) | Alembic 마이그레이션, 기능 명세 데이터 요구사항 |
| 화면 추가 | IA 사이트맵·이동 경로, 와이어프레임, UI 시안 §4 |
| 스프린트 구성 변경(plan.md) | 이 README §2.2, RTM 스프린트 열 |
| `DESIGN.md` 토큰 변경 | UI 시안 §1·§6 |
